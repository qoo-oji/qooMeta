# ファイル名フォーマット(提案)

2026-09-19。**名前のどの部分を何の欄とみなすか(捨てるかを含む)は、利用者がファイル名フォーマットで決める。** 雑多な情報(`[DL版]`
など)の扱いも、フォーマットに `@info` と書けば情報の欄に残る(`@ignore` なら捨てる)、というだけのことになる。
qooMeta 側で「雑多な情報」を別に扱う仕組みは作らない。

**土台は、ターゲットの 3 つのアプリ(qooViewer・StackNest・ShelfRow)のフォーマットの書き方**で、これは要件(型を持ち運べるように
同じ書き方にする)。qooLibrary はターゲットではなく参考で、書き方も語もコードも持ってこない(concept.md「ターゲットと参考」)。
照合の処理は、下の 1 の書き方だけを読むものを qooMeta で書く(写してあった `Sources/QooFormat` は捨てる)。

## 1. 書き方

### ターゲットの 3 つのアプリに共通する部分(要件)

| 項目 | 内容 | どのアプリにあるか |
|---|---|---|
| 予約語で欄を指す | `[@author] @title (@source)` のように、欄の位置を予約語で書く。予約語以外の文字はそのまま照合する | 3 つとも |
| フォーマットの並び | 上から照合し、名前全体に一致した最初のものを採る | qooViewer(並び)、StackNest(名前付きで複数) |
| 括弧 | `[ ]` と `( )` の中に予約語を書く。括弧の中の括弧(`[@author (@author)]`)も書ける | 3 つとも(入れ子は ShelfRow・qooViewer) |
| 空白 | フォーマットの空白は「0 文字以上の空白」 | 3 つとも |
| 読まない部分 | `@ignore`。何度でも書ける | qooViewer |

### qooMeta で足すもの

ターゲットの書き方に無く、qooMeta の役目(合わなかった名前を見つけて型を直す)のために足すもの。

| 足すもの | 理由 |
|---|---|
| 最も近いフォーマットを示す | どの型にも合わなかった名前を直すとき、どこで外れたかを見せるため |
| 全角と半角の括弧(`()` と `（）`、`[]` と `［］`)を同じとみなす | 書き手の入力の揺れで、意味は同じ。空白と同じ扱い |

照合の細かい決まり(qooMeta の実装。2026-09-19):

- 括弧の中に書いた欄の値には、その括弧の対の文字(全角・半角とも)を含めない(`(@source)` の値に `(` `)` は入らない)。
- **`@volume` は、巻数とみなせる値にだけ当たる**。何が巻数かを決めるのはこちらではなく、`series-rules.json` の
  巻の読み手(`volume.readers` に登録した語)。巻数に変換する文字列の設定があるのだから、そこに無い文字列は通さない
  (2026-09-21、利用者の指示)。数字のほか、漢数字や「上・中・下」も、読み手に登録してあれば当たる。語はコードに書かない
  (concept.md の原則 8)。全角の括弧と全角の数字は半角に畳んでから照合し、巻数の値も半角にそろえる(「（１２）」は巻数 `12`)。ほかの欄の値は、名前に書かれたままの文字で持つ(表示の形にそろえるだけ)。
  括弧の外の欄(`@title`)には何でも入る。
- 欄は長く取るほうを先に試す。区切りの文字が何度も現れる名前は、最後のもので分ける(`@title - @author` で `A - B - C` なら
  タイトル `A - B`)。
- 欄と欄のあいだには、空白のほかの文字が要る(`@title @author` は書けない。どこで分けるかが決まらない)。型には `@title` か
  `@series` が要る。**`@title` の無い型**(`@series (@volume) - @author`)で読んだ本のタイトルは、型の `@series` から `@volume` までの部分
  (じかに付いた括弧などの文字も含む)に読んだ値をはめたものにする(「月の庭 (3)」。`@series 第@volume巻` なら「月の庭 第3巻」。
  2026-09-20、利用者の指示)。型に書いた文字を使うので、名前の側の括弧が全角でも、同じ型で読んだ本は同じ形にそろう。
- 著者の値は区切り(既定は `,` `，` `、`)で分ける。全角のカンマは `,` の幅の違いとして同じに扱う。並びの欄は著者だけで、
  ほかの欄の値は区切りで分けない。**区切りは型ごとに決められる**(4 の「区切りと既定の欄の優先順位」)。
- 最も近い型は、型の頭から満たした部品がいちばん多いもの(同じなら、読めた文字が多いもの、上のもの)。どの型も最初の部品から
  外れる名前(括弧の無い名前など)には、近い型を示さない。`@title` で始まる型は、どんな名前でも頭の欄までは「合う」ので、
  頭の欄の次の文字まで進んだときだけ近い型の候補にする。

足さないもの: `「」` `【】` を括弧として特別に扱うこと、` - ` `_` `＿` を区切りとして特別に扱うこと(これまでの案にあった)。`「」` は本では
タイトルの一部であることが多く、構造として読むと題名を壊す(先方でこれを構造に使っているのは動画のサブタイトル)。`【】` や ` - ` を
使う命名の利用者は、予約語以外の文字はそのまま照合されるので、`【@ignore】 @title` のように型に書けば足りる。

**タイトルの中のシリーズ名と巻数は、フォーマットでは読まない。** 名前の形として定式化できない(同じ形でも巻だったり題名の一部だったり
する)ので、規則の JSON で扱う(3)。ただし、名前の中に**はっきり書いてある**ときは `@series` `@volume` で読める(2026-09-20、利用者の判断)。
読んだ値は、利用者が確定した値と同じ扱いで中核へ渡す(巻数を読んだ本は、比べるタイトルの後ろにその表記を付けるので、
「タイトル + 巻」の規則がそのまま効く)。`@season` `@episode` `@subtitle` `@actor` など動画向けの語も取り入れない。

## 2. 予約語

**StackNest・ShelfRow の予約語を土台に**し、足りない分を補う。

| 予約語 | 欄 | 出どころ | 備考 |
|---|---|---|---|
| `@title` | タイトル | StackNest・ShelfRow | |
| `@author` | 著者 | StackNest・ShelfRow | 何度でも書ける。値は区切りで分けて、書いた順・読んだ順に並べる(下) |
| `@genre` | ジャンル(本の種類) | StackNest・ShelfRow | ほかの欄と同じ自由な文字列 |
| `@event` | イベント(頒布会の名前) | 足す(qooMeta) | ターゲットの 3 アプリに無い欄。同梱の型は使わない。先頭の丸括弧に頒布会の名前を書く利用者が、型で `(@event)` と書く(2026-09-20、利用者の判断。先頭の丸括弧に頒布会の名前を書く利用者がいるため) |
| `@source` | 原作(二次創作の元作品) | StackNest・ShelfRow の `@relation` | 綴りだけ変える(下) |
| `@series` | シリーズ | 足す(qooMeta) | 名前にシリーズ名がはっきり書いてあるときだけ。読んだ値は、利用者が確定した値と同じ扱いで中核へ渡す(タイトルから導く処理を通らない)。`@series` を書いた型は `@title` を省ける(2026-09-20、利用者の判断) |
| `@volume` | 巻数(表示用) | 足す(qooMeta) | **巻の読み手が巻数と認めた値にだけ当たる**(全角の数字は半角に畳む)。商業の本の「(12)」を巻数として読む。読んだ値は確定した値と同じ扱い(2026-09-20、利用者の判断) |
| `@info` | 情報(ほかの欄のどれでもない部分) | 足す(qooMeta) | 同梱の型は末尾の角括弧に使う(2026-09-20、利用者の判断。「メモ」は ShelfRow の欄に引っ張られた名前だった。読んだ時点では何も捨てず、書き出し先に合う欄が無ければ書き出しの対応表で捨てる) |
| `@ignore` | (捨てる) | 補う(qooViewer) | 何度でも書ける。同梱の型は使わない |

- StackNest の `@series` `@volume` は置かない。シリーズと巻はタイトルから規則の JSON で導く(3)。StackNest のテンプレートを取り込むときは、
  その部分を `@title` へまとめる(StackNest 自身も取り込みで捨てている)。
- `@relation` は `@source` と綴る(2026-09-19 決定)。中身は二次創作の元作品(英語圏では source material)。`@original` は、同人誌で
  この欄に「オリジナル」(二次創作ではない)と書かれるものと紛れ、`@parody` は日本では二次創作と違う印象を持たれるため採らない。
  StackNest・ShelfRow のテンプレートを取り込むときは `@relation` を `@source` に読み替え、書き出すときは戻す。
- メモの欄は持たない(情報の欄で足りる)。
- `@keywordA` `@keywordB` `@keywordC` は置かない(2026-09-20、利用者の判断。書き出し先ごとの違いを書き出しの対応表で振り分けると決めたので、利用先の意味の決まらない入れ物は欄にしない。StackNest・ShelfRow のテンプレートを取り込むときは `@info` に読み替える)。
- 同じ予約語を 1 つのフォーマットに 2 度書けるのは `@author` と `@ignore` だけ。
- **著者の区切り**: `[@author (@author)]` の括弧と、`,` `、`(2026-09-19 決定)。設定で足せる。`×` `&` `・` は 1 つの名義(ユニット名・
  サークル名)の中にも現れ、取り違えると著者の先頭(中核の比べる単位)が壊れるので、既定には入れない(同梱の型と同じ基準。5)。
  `[作画×原作]` の形が多い利用者は設定で `×` を足す。分けなくても、1 つの名義として一貫して同じ単位になるので、シリーズは崩れない。
- これまでの `@circle` は撤去する(サークル名は `@author` の先頭)。`@event` は、いったん撤去としたが、イベントの欄として持つ
  ことにした(2026-09-20、利用者の判断。先頭の丸括弧に頒布会の名前を書く利用者がいるため)。書き出し先のアプリにはイベントの欄が無いので、書き出しのプレビューで「落ちる欄」として示す。

## 3. シリーズと巻

**タイトルからシリーズ名と巻数を取り出す処理は qooMeta の中核**で、ほかのアプリ(qooLibrary・qooViewer・StackNest)のやり方に寄せない。
シリーズと巻は名前の形として定式化できない(同じ形でも巻だったり題名の一部だったりする)から、qooMeta は複雑な条件を書ける規則の JSON
(`Sources/QooMetaRules/Resources/series-rules.json`、利用者の変更は差分で重ねる)と、ほかの本と見比べる仕組みで扱っている。

- フォーマットは欄の位置を読むところまで。シリーズと巻は、フォーマットで読んだタイトルと著者の並びを入力に、今の規則と仕組みで導く。
- 見直しで変わるのは入力の欄の名前(サークル → 著者の並びの先頭 …)だけで、規則の中身と仕組みは変えない。
- qooViewer の除外文字列・巻数フォーマットは、フォーマットの取り込みの対象にしない(用途は近いが、規則に写すと中核の考え方が崩れる)。

## 4. 設定の持ち方・プリセット・持ち運び

### JSON の形(`filename-formats.json`、第 6 版。2026-09-21)

```json
{
  "kind": "qoometa.filename-formats",
  "schemaVersion": 6,
  "defaultPreset": "commercial",
  "presets": {
    "commercial": {
      "separators": [",", "，", "、"],
      "formats": [
        "[@author] @series (@volume)",
        "[@author] @title",
        { "format": "@series (@volume) - @author", "separators": ["×", "&"] }
      ]
    },
    "doujinshi-event": {
      "separators": [",", "，", "、"],
      "defaults": { "genre": "同人誌" },
      "formats": ["(@event) [@author] @title (@source)", "…"]
    }
  }
}
```

| キー | 書ける場所 | 意味 |
|---|---|---|
| `defaultPreset` | ファイル全体 | 本がプリセットを選ばなかったときに使う名前 |
| `presets` | ファイル全体 | 名前 → プリセット。**名前は自由**(利用者は差分で新しい名前のプリセットを足せる) |
| `label`・`note` | プリセット | 画面に出す見出しと説明(省ける)。**同梱のプリセットは書かない**(アプリが利用者の言語で出す。2026-09-21)。利用者が書いた見出しは、その言葉のまま出る |
| `formats` | プリセット | 型の並び。**上から照合し、名前全体に一致した最初の型で読む**(並び順が優先順位) |
| `format` | 型(オブジェクトで書いたとき) | 型の文字列。区切りも既定も添えない型は、文字列だけを書く |
| `separators` | プリセット・型 | 著者の値を分ける文字列(1 文字とは限らない) |
| `defaults` | プリセット・型 | 名前に書かれていない欄に入れる値(ジャンル・イベント・原作・情報) |
| `plain` | プリセット・型 | **型として読まない文字列**(`words` と `patterns`)。下の「型として読まない文字列」 |

### 区切りと既定の欄の優先順位

`separators` と `defaults` は、**同じ綴りで 2 か所に書け、内側に書いたものが勝つ**。決まりはこれだけ:

```
型(その型で読んだ本だけ) > プリセット
```

第 6 版で**ファイル全体の段をやめた**(2026-09-21、利用者の指示)。区切りも既定の欄も「解析のしかた」の一部で、
プリセット(ルールセット)を選ぶことが解析のしかたを選ぶこと ―― 外にもう 1 段あると、どのプリセットを選んでも
共通に効く設定が別の場所にあることになり、画面でも JSON でも見通しが悪かった。

- **`separators` は、書いた所で丸ごと置き換わる**(足し合わせない)。型に `["×"]` と書けば、その型で読んだ著者は `×` だけで分け、
  `,` では分けない。`,` でも分けたいなら `[",", "×"]` と書く。書かなければ、1 つ外側の区切りをそのまま使う。
- **`defaults` は欄ごと**。型が `genre` だけを書けば、`genre` は型の値、ほかの欄はプリセットの値。
- **名前から読めた値が、どの既定よりも強い**(既定は空の欄にだけ入る)。どの型にも合わなかった名前には、プリセットまでの既定が入る。
- 型の中で読み方を決める順は「① 並びの上から最初に一致した型 → ② その型の区切りで著者を分ける → ③ 空の欄に既定を入れる」。

区切りを型ごとに決められるようにしたのは、同じ字が命名の形によって意味を変えるため(2026-09-20、利用者の指示)。`×` は、
角括弧の中では 1 つの名義(ユニット名)の一部のことが多いが、「シリーズ名 (12) - 著者」の形の本では連名の区切りのことがある。

### 型として読まない文字列(`plain`。2026-09-20、利用者の指摘)

名前の中の**この部分は、型の照合のあいだだけ、ただの文字として扱う**: 括弧であっても型の括弧には当たらず、欄の区切りにも
ならない。値からは消えない(タイトルなどの一部として、そのまま残る)。

```json
"plain": { "words": ["(仮)"], "patterns": ["[(（](?:19|20)\\d{2}年?[)）]"] }
```

- 要るのは、**欄として読まれる位置(名前の末尾など)に、欄ではない括弧が来る**とき。「月の庭 (2026)」の「(2026)」は年だが、
  末尾の丸括弧なので、同人誌の並びでは原作、商業誌の並びでは巻数として読まれていた。
- タイトルの**途中**の括弧には、もともと要らない: `@title` は括弧の外の欄で何でも入るので、
  「月の庭 旧版（2022年）＋新版（2025年） (架空の原作)」は、何もしなくてもタイトルに年が残り、末尾の丸括弧だけが原作になる。
- **同梱の既定は、丸括弧の中の西暦(1900〜2099 年。「年」付きも、全角の括弧も)**。巻数としてはまず現れない数で、年として
  書かれることが多いため。年ではない数字の丸括弧(「(12)」)は、これまでどおり巻数として読む。
- `plain` は プリセット → 型 と**足し合わさる**(区切りや既定の欄と違い、内側が外側を打ち消さない。
  どの文字列を型として読まないかは、足していくものだから)。
- 効くのは型の照合だけ。**タイトルからシリーズと巻を導く規則には効かない**(残った「(2026)」を巻として読むかどうかは、
  series-rules の側の話。読ませたくなければ、そちらの「そのまま読む語」に足す)。
- `@volume`(巻数の欄)には入らない。正規表現は、ほかの規則の正規表現と同じ安全の検査を通る。

### 差分(利用者の変更)の書き方

同梱の既定値に重ねる差分(`"base": "builtin"`)では、

- **同梱のプリセットを変える**: 名前で指し、配列は操作で書く。
  `{ "presets": { "commercial": { "formats": { "$add": ["…"], "at": "end" }, "separators": { "$add": ["×"] } } } }`。
  `formats` の `$add` は `"at": "start"`(既定。利用者の型を先に試す)か `"end"`。置き換えは `{ "$replace": [...] }`。
  型は **`format` の文字列で見分ける**(区切りを添えた型も、`$remove` に文字列だけを書けば外せる。同じ型は 2 つにならない)。
- **新しいプリセットを足す**: 同梱に無い名前で、**全体**を書く(`{ "my-shelf": { "label": "…", "formats": ["…"] } }`)。
  重ねる相手が無いので `$add` などは書けない(同梱の名前の書き間違いを、新しいプリセットとして黙って受け取らないためでもある)。
- `defaultPreset` も置き換えられる(ある名前でなければ誤り)。`defaults` は欄ごとに置き換え、`null` でその欄の既定を消す。

### 設定の持ち方

- **qooMeta にはライブラリが無い**(開いたファイルの一覧からメタデータを作って書き出すだけ)。だから、フォーマットの並びと規則の差分は
  **アプリの設定**として 1 組持つ(qooViewer と同じ)。StackNest のライブラリごとのテンプレートや qooLibrary の
  ライブラリ単位の設定には合わせない。命名の違う本が混ざっていても、並びの上から名前全体に一致した最初の型で読むので、並び 1 つで足りる。
- 同梱するのは型の並び 1 つ(5)。利用者はそれを複製し、並べ替え・書き足しをする(同梱のものは書き換えない)。
- 取り込み: qooViewer の JSON のファイル名フォーマット、StackNest のテンプレート、ShelfRow のフォーマット
  文字列を読み込めるようにする(予約語の綴りが同じなので、ほぼそのまま移せる)。除外文字列・巻数フォーマットは取り込まない(3)。
- 書き出し: qooMeta で詰めたフォーマットを、各アプリの形式でも書き出せるようにする(各アプリの予約語に無い欄は、そのアプリの `@ignore` にあたるものにする)。

## 5. 同梱するプリセット

同梱するのは、**命名の違う本が混ざった蔵書をそのまま読む、型の並び 1 つ**。本の種類ごとの組(コミック用・同人誌用 …)には分けない
(原則 1。種類ごとの組は、ライブラリを種類で分ける qooLibrary の考え方で、qooMeta にはライブラリが無い)。

### 出発点はターゲットの既定

qooViewer の既定のフォーマットは 12 通り(`Models/MetadataFormatRule.swift`)。先頭の丸括弧・著者の後ろの丸括弧・末尾の丸括弧・
末尾の角括弧の有無の組み合わせを、具体的なものから順に並べている。読むのは著者とタイトルだけで、ほかの位置は `@ignore`:

```
(@ignore) [@author (@ignore)] @title (@ignore) [@ignore]
(@ignore) [@author (@ignore)] @title (@ignore)
(@ignore) [@author (@ignore)] @title
  … ([@author] だけの 3 通り、先頭の丸括弧が無い 6 通り)
[@author] @title
```

ShelfRow の既定は `[@author] @title`、合わないときの固定の読み方は `(ジャンル)[作者]タイトル`(末尾の角括弧は捨て、末尾の丸括弧は読まない)。
ターゲットが前提にしている名前の形は、この 12 通りに収まる。qooMeta の同梱の並びは、**この形を土台に、`@ignore` の位置へ qooMeta の欄を
割り当てたもの**にする。

### 位置ごとの割り当て

| 位置 | 既定の欄 | 理由 |
|---|---|---|
| 先頭の丸括弧 | `@genre` | ShelfRow の固定の読み方がジャンルとして読む。StackNest でも利用者は本の種別に使っている。イベント名などが入る名前もあるが、形では見分けられないので、値の列で気づいてまとめて直す(roadmap.md のジャンルについての決定) |
| 角括弧の中の丸括弧 | `@author`(2 つ目以降) | 名義が複数ある(metadata.md の 2)。StackNest は著者が複数値 |
| 末尾の丸括弧 | `@source` | StackNest(neta)・ShelfRow(関連)に原作の欄があり、中核も方針 `differentRelation` で使う |
| 末尾の角括弧 | `@info` | 付記(入手経路など)。読んだ時点では捨てず、情報の欄に残す(書き出し先に合う欄が無ければ対応表で捨てる) |

### 参考(qooLibrary のプリセット)を吟味した結果

qooLibrary のプリセットは、実際の蔵書と突き合わせて直されてきたもので、命名についての知識が入っている。そのまま使わず、1 つずつ
qooMeta に要るかを見た。

| qooLibrary のプリセットにあること | qooMeta での扱い |
|---|---|
| 名前の形は「先頭の丸括弧 / 角括弧(中に丸括弧)/ タイトル / 末尾の丸括弧 / 末尾の角括弧」の有無の組み合わせ | **同じ結論**。ターゲットの qooViewer の 12 通りと同じ形で、裏づけになる |
| 末尾の丸括弧が無く、末尾の角括弧だけがある形(`… @title [付記]`)。qooViewer の 12 通りには無い | **取り入れる**。理由は下の「同梱の並び」(qooMeta ではタイトルに付記を残せない) |
| 先頭の丸括弧は、本の種別のこともイベント名のこともある。語の一覧で見分けないと、取り違えが 1 割を超える(先方の実測) | **知識だけ取り入れる**。語の一覧は持たない(決定済み)。取り違えが珍しくないと分かっているので、値の列で見つけてまとめて直す流れを、骨組みの画面(roadmap.md の段階 5)で最初から確かめる |
| `@title` だけの型は入れない(何にでも一致して、直すべき名前が「読めた」ことになって埋もれる。先方の実測でも裏づけ) | **取り入れる**。qooMeta でも、合わなかった名前は型を直す入口なので、埋もれさせない |
| 具体的な型を上、緩い型を下に並べる | **取り入れる**(qooViewer の既定も同じ並べ方) |
| 本の種類ごとにプリセットを分ける(4 組)。フォルダ名の型。種類ごとの巻の表記の組 | **取り入れない**。ライブラリを種類で分ける前提のもの。qooMeta は並び 1 つ、フォルダ名は読まない、巻は中核の規則 |
| サークルと著者を別の欄にする(`@studio` `@author`)。キーワードの欄が 1 つ | **取り入れない**。欄はターゲットの和集合(metadata.md の 2) |
| イベントの欄(`@event`) | **取り入れる**(2026-09-20、利用者の判断)。ターゲットには無いが、先頭の丸括弧に頒布会の名前を書く利用者がいる。同梱の型は使わない |
| 動画のプリセット | **取り入れない**(本ではない) |

### 選ぶ基準

型を同梱するかどうかは、一致する冊数ではなく、**取り違えたときに何が壊れるか**で決める。同梱の並びは利用者が何も考えずに最初に使うもの
なので、

- 形から意味がほぼ決まる型、または取り違えても**タイトルと著者は正しく**、ずれるのが脇の欄(ジャンル・原作)だけの型は入れる。
  脇の欄のずれは値の列で目に見え、まとめて直せる。
- 取り違えると**タイトルや著者そのものが壊れる**型は入れない。壊れた著者は中核の比べる単位になり、静かにシリーズを崩す。
  そういう名前は「合わなかった名前」に出るほうがよい(利用者が自分の命名に合わせて型を足す)。

### 同梱の並び(4 つ)

**プリセットは同人誌用と商業誌用に分ける**(2026-09-20、利用者の判断)。末尾の丸括弧が原作なのは同人誌の慣習で、
商業の本では巻数のことが多い。著者の中の丸括弧(`[@author (@author)]`)も同人誌固有なので、商業誌用には入れない。
**両方をまとめた「混ざった蔵書」用の並びは同梱しない**(2026-09-21、利用者の判断)。プリセットを分けたいものは、
そもそも一緒に読み込まない。まとめた並びは、どの名前にも緩く当たるので「読めた冊数」が当てにならず、
どのプリセットを選ぶかの手がかりを壊していた。要る利用者は、プリセットの編集画面で自分の並びを作れる。

さらに、**同人誌用は先頭の丸括弧の読み方で 2 つに分かれる**(2026-09-20、利用者の判断)。先頭の丸括弧にジャンルを書く利用者と、
**頒布会(催し)の名前**を書く利用者がいて、どちらも「(…)」という同じ形なので、**1 つの並びには同居できない**
(先に当たったほうで読んでしまう)。どちらで管理しているかは蔵書ごと・フォルダごとに決まっているので、並びを分けて選べるようにする。

| プリセット | 名前 | 中身 |
|---|---|---|
| 同人誌用(ジャンル) | `doujinshi` | 先頭の丸括弧はジャンル。末尾の丸括弧は原作。著者の中の丸括弧を読む。16 通り(下) |
| 同人誌用(催し) | `doujinshi-event` | 先頭の丸括弧を**催しの名前**(`@event`)として読む。ほかは `doujinshi` と同じ 16 通り |
| 商業誌用 | `commercial` | 末尾の丸括弧は巻数(巻の読み手が認めた値)。手前は **`@series`**。原作と、著者の中の丸括弧(同人誌固有)は使わない。先頭の丸括弧はジャンル。末尾に「シリーズ名 (巻数) - 著者」の 2 通り(下)。10 通り |

**「シリーズ名 (巻数) - 著者」の形**(2026-09-20、利用者の指示。商業誌用と既定の並びの末尾に入れた):

```
@series (@volume) - @author [@info]
@series (@volume) - @author
```

著者を末尾に ` - ` で付ける命名。丸括弧の前はシリーズ名そのものなので **`@series` で読む**。読んだシリーズと巻数は利用者が
確定した値と同じ扱いになり、**タイトルからシリーズと巻を導く処理を丸ごと通らない**(「X 総集編 (2)」も、書いてあるとおり
シリーズ「X 総集編」の 2 巻)。`@title` の無い型なので、タイトルは型のその部分に値をはめた「月の庭 (3)」になる(1 の「照合の細かい決まり」)。
**巻数の丸括弧のすぐ後ろ**に ` - ` が続くときだけ当たるので、「題名 - 副題」の副題を著者に取り違えない(選ぶ基準を満たす。
括弧の無い `@title - @author` は、下のとおり入れない)。角括弧で始まる形と両方に当たる名前は、これまでどおり角括弧の形で
読むように、並びの末尾に置く。末尾の角括弧が著者に入らないよう、`[@info]` の付いた形を先に試す。

**プリセットは、名前に書かれていない欄の既定値を持てる**(2026-09-20、利用者の判断)。催しの並び(`doujinshi-event`)では
ジャンルがどの名前にも書かれないが、そういう蔵書は丸ごと同人誌なので、**ジャンルの既定を「同人誌」にする**。
既定はプリセットの定義(JSON)に書き、コードには持たない。名前から読めた欄は既定で上書きしない。
どの型にも合わなかった名前にも既定は入る(その蔵書がどういう本かは、型に合ったかどうかで変わらないため)。

```json
"presets": {
  "doujinshi-event": {
    "defaults": { "genre": "同人誌" },
    "formats": ["(@event) [@author] @title (@source)", "…"]
  }
}
```

既定を書ける欄は ジャンル・イベント・原作・情報 の 4 つ(タイトルと著者は本ごとに違う。シリーズと巻は中核が導く)。
既定はファイル全体と型にも書ける(4 の「区切りと既定の欄の優先順位」)。

**プリセットは本ごとに選べる**が、**画面では蔵書の全体に 1 つを選ぶだけ**にした(2026-09-21、利用者の判断。プリセットを分けたい
ものを 1 度に読み込むべきではない)。フォルダごとの割り当ては、確かめ用に CLI の `--presets <割り当て.json>` に残す
(割り当てには蔵書のフォルダ名が入るので、リポジトリの外に置く)。形式(作業ファイルの `presets.folders`)はそのままで、
アプリは読むが編集しない。

同人誌用:

```
(@genre) [@author (@author)] @title (@source) [@info]
(@genre) [@author (@author)] @title (@source)
(@genre) [@author (@author)] @title [@info]
(@genre) [@author (@author)] @title
(@genre) [@author] @title (@source) [@info]
(@genre) [@author] @title (@source)
(@genre) [@author] @title [@info]
(@genre) [@author] @title
[@author (@author)] @title (@source) [@info]
  … (先頭の丸括弧が無い 8 通り。同じ順)
```

qooViewer の 12 通りに、**末尾が角括弧だけの形**(`… @title [@info]`)の 4 通りを足した 16 通り。qooViewer に無いのは、著者とタイトルしか
使わない閲覧アプリでは付記がタイトルに残っても困らないから。qooMeta のタイトルは書き出し(EPUB・PDF の題名)と中核の入力になるので、
タイトルに付記を残さず、情報の欄へ分ける。取り違え(題名が本当に `[…]` で終わる本)は稀で、起きてもタイトルの末尾が情報の欄へ移るだけで、一覧で見える。

入れないもの:

- `@title - @author`(作者が末尾に ` - ` で付く形。これまでの案では足すとしていた)。括弧の無い名前で ` - ` を含むものすべてに一致するので、
  「題名 - 副題」の本の副題を著者に取り違える。タイトルも著者も壊れ、しかも「読めた」ことになって埋もれる。この命名を使う利用者が
  自分で足す型(区切りが複数あるときは最後のもので分ける、という読み方だけは用意する)。数字だけの丸括弧を挟む
  `@series (@volume) - @author` は、この取り違えが無いので入れた(上)。
- `@title [@author]`(作者が末尾の角括弧)。末尾の角括弧が作者か付記かは形で決まらず、取り違えると著者が壊れる。
- `@title`(タイトルだけ)。何にでも一致して、直すべき名前が埋もれる。

**残る弱点(利用者に見える形にして、設定で逃がす)**: 末尾の丸括弧を `@source` と読むのは二次創作の本の慣習で、商業の本では末尾の丸括弧が
別の意味(レーベル・版など)のことがある。取り違えてもタイトルと著者は正しいが、中核は原作が違う本を分ける(方針 `differentRelation`)ので、
シリーズが割れうる。ジャンルと同じ扱いにする: 値の列で見つけてまとめて直せ、方針は設定で `keep` にできる。商業の本の多いフォルダでの
集計(roadmap.md の段階 1)で、この取り違えがどのくらい起きるかを先に測る。

集計(roadmap.md の段階 4)は採否を決めるためではなく、確かめるために取る: 型ごとの一致冊数と、どの型にも合わなかった冊数。合わなかった
冊数が多ければ、その名前の形(文字種に置き換えたもの)を見て、基準に照らして型を足すかを考える。

## 6. これまでの qooMeta から変わること

| これまで | これから |
|---|---|
| 予約語の対応表が意味とずれていた(`@genre` → 照合の処理の `@mediatype`、`@relation` → `@genre` …) | 予約語 = qooMeta の欄。照合の処理の内部の名前は利用者に見せない |
| `@ignore` を外に出していなかった | 使える(シリーズと巻は予約語にせず、規則で導く) |
| 同人誌の 1 組と「括弧の位置だけで読む」予備 | 利用者の並べた型。どれにも合わなければ「合わなかった名前」として直す対象に出す |
| 版・入手経路の印を、欄とは別の仕組みで見分けていた | 名前の中の印をどの欄に入れるか(捨てるか)はフォーマットで決める(`[@info]`・`[@ignore]` …)。タイトルの中に残る印を比べるときに除くのは、今の規則のまま(3) |
| フォルダ名は書き手の代わりにだけ使っていた | フォルダ名は読まない(2026-09-19 決定。3 つのアプリはどれもフォルダ名を読まない。フォルダ名の型は qooLibrary 固有) |
