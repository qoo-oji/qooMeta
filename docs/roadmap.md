# 実装計画

2026-09-19 時点の計画。qooMeta は最終的に次の 2 つの形で使えるようにする。

1. **ライブラリ**: 依存パッケージとして qooViewer に組み込み、qooViewer がファイル名からメタデータを作るのに使う。
   qooViewer の今のファイル名の規則(ファイル名フォーマット・除外文字列・巻数フォーマット)は、最終的に qooMeta に置き換える。
   StackNest や ShelfRow のような蔵書管理アプリに組み込んでも十分に使える、汎用の API にする。**qooViewer への組み込みの時期は未定**。
2. **単独の GUI アプリ**: qooViewer とは独立させ、StackNest や ShelfRow の利用者も使えるようにする。このリポジトリの `App/` に置く。

関連する設計: [rules-format-design.md](rules-format-design.md)(規則ファイルの形式の第 2 版)、[api.md](api.md)(API 仕様)。

## 構成

```
qooMeta
├─ QooMetaKit      本体。名前の解析・シリーズ・巻・版・推定、規則の組み立てと検証、規則のカタログ、説明、
│                  ProposalIndex、フィードバックの例づくり。Foundation だけに依存し、macOS 15 以降。QooFormat は内部に置く
├─ QooMetaRules    同梱の既定値のデータ、利用者の変更(差分)の編集、rules-bundle、例の確認、システムの辞書の読み込み口
├─ QooMetaExport   Stackroom XML・qooViewer JSON・ComicInfo。Data を返す
├─ QooMetaScan     フォルダの走査(名前と属性だけ)
├─ QooMetaAI       端末内モデル(任意、macOS 26 以降)
├─ qoometa         CLI(検証・一括処理・規則の確認)
└─ App/            GUI アプリ(SwiftUI)
```

## 進め方の約束(全段階に共通)

- **持ち運べる確認手段は例のファイル**(架空の名前。リポジトリに入り、CI でも走る)。規則や処理を変える前に、確かめたい形を例に足す。
- **結果を変えない移し替え**では、手元の 2 つの蔵書と公開データでも「本と組の中身」が 1 冊も変わらないことを確かめる
  (前後の出力のハッシュを比べる。名前は出さない)。これはこのマシンでしかできないので、例のファイルの代わりにはしない。
- 例・テストの名前は架空のものだけ。コミットの前に禁止語の検査を通す。
- 説明の文書(rules.md・api.md)は、実装と同じ変更の中で直す。

## 段階 0: 規則ファイルの土台(形式の第 2 版)

規則は最初のサンプルにすぎず、利用者のフィードバックで中身を育て、形式も広げていく。その土台を先に作る。
利用者がまだいないので、作り込みすぎない(rules-format-design.md「最初の実装に入れるもの・後回しにするもの」)。

1. **例のファイルを先に作る。** これまでに直してきた形(番号の無い 1 冊目、総集編、版違い、ネタ違い、1 語だけの一致、
   一般的な英語だけのタイトル、雑誌の号と合併号、分冊、上中下、括弧を含む名前 …)を、架空の名前で `qoometa.examples` に起こす。
   「シリーズに入ってはいけない」(`"series": null`)の例を含める。今の単体テストのうち移せるものを移す。`qoometa rules test`。
2. **CI を入れる**(GitHub Actions): `swift build`・`swift test`・`rules test`、一般的な形の検査(個人のパスなど。禁止語の一覧は
   手元にしか無いので CI では使えない)、本体の静的検査(下の段階 1 の 2)。CONTRIBUTING に、例と報告には架空の名前だけを書く約束を書く。
3. 読み込みの流れ: 型なしで読む → `schemaVersion` を見る → 既定値に差分を重ねる → 検証する(誤りをすべて集める。位置と近い綴りの候補) → 組み立てる。
4. 版の番号: `schemaVersion`・`engineLevel`・`since`・`required`。ID の約束(`retiredIDs`・`aliases`)。
5. **認識と方針を分ける**: 好みで決まる扱い(版・入手経路・総集編・雑誌・1 巻の推定・ネタや本の種別の違い・副題付き)を `policies` に出す。
   既定値は今の扱い。既定でない値(総集編を本編に含める、版違いを別の本として数える …)の動きも実装し、方針ごとの例で確かめる。
6. 固定の段階と、ID の付いた規則のオン・オフ・パラメータ。例外は親の規則の `conditions` に置く。巻の読み手だけ並べ替えられる。
   埋め込みの読み方は、まずオン・オフだけを外に出す。
7. 語の一覧と文字の集合を `lists` に集める。差分の操作(`$add`/`$remove`/`$set`/`$unset`/`$replace`/`$order`)。
8. ファイル名のフォーマットをプロファイルに分ける(今は同人誌向けの 1 つ)。
9. 辞書を名前で指す形にし、実体は呼び出し側が渡す(規則ファイルからパスをなくす)。
10. 同梱の既定値を第 2 版で書き直す。規則の上限と正規表現の安全性の検査。
11. CLI: `rules validate`・`rules show`(重ねた結果と、どちらの値が効いているか)・`rules test`。JSON Schema は手で書いて `schema/` に置く。
12. docs/rules.md を第 2 版の説明に書き直す。

後回し: 第 1 版からのマイグレーション、埋め込みの読み方の細かいパラメータ、プロファイルの適用の条件、JSON Schema の自動生成。

**終わりの条件**: 例のファイルが全部通り、CI で走る。第 2 版の既定値で、手元の蔵書と公開データの結果が今と同じ。
書き間違いの JSON で、すべての誤りの位置と候補が出る。廃止した ID を参照する差分が、エラーにならず警告で読める。

## 段階 1: ライブラリとして使える形にする(api.md)

1. モジュールを分ける(QooMetaKit / QooMetaRules / QooMetaExport / QooMetaScan / QooMetaAI)。本体は macOS 15 以降、Swift 6.2 以降。
2. 本体を純粋な計算にする: グローバルな状態(今の `RuleFiles` の固定の読み込み)をなくし、規則・語彙・辞書を値で受け取る。
   **CI の静的検査**で、本体のソースに `FileManager`・`URLSession`・`print`・`os_log` などが無いことを確かめる。
3. 入力を `BookInput` と `Confirmation`(確定した内容)にする。確定した値の効き方(錨・組を割る・シリーズではない)を実装し、例で確かめる。
4. `parseName`、`proposeSync` / `propose`(取り消し・進み具合)、`ProposalIndex`(全か無か。一括の計算と同じ結果になることをテストで確かめる)。
5. 出力を `ProposalSet` / `BookProposal` / `SeriesProposal` / `Volume` にし、決まった順で返す。`SeriesID` は保存しない約束。
   単位をまたぐ情報(ありふれた言葉の疑い)は提案から外し、別の問い合わせにする。
6. 説明(`Explanation`・`NearMiss`): なぜ組になったか、なぜならなかったか。
7. 規則のカタログ(`RuleCatalog`)と、利用者の変更(`RuleChanges`)。規則ごとの初期化。
8. `makeFeedbackExample`: 全語を置き換える規則と、置き換えた例が元と同じ結果になることの確認。
9. `QooMetaExport`: Stackroom XML・qooViewer JSON・ComicInfo。第三者のアプリの欄への対応表は入れない(GUI アプリに置く)。
10. 入力の上限、正規表現の時間の上限。並列化は単位をまとめた塊ごと。
11. CLI を新しい API の上に作り直す。`qoometa bench` で測る(1 万冊の一括、1 冊の追加)。`public` の整理。

**終わりの条件**: 例のファイルと CLI の結果が段階 0 と同じ。静的検査が通る。性能の目安を測って docs に書く。

## 段階 2: GUI アプリ

最初に**プレビュー一覧**を作る(利用者の要望。CSV は見づらいので、見直しは GUI で行う)。

- **プレビュー一覧**: 左にシリーズの一覧(シリーズ名・サークル・冊数・巻の範囲・推定の有無)、右に選んだシリーズの本の一覧
  (巻・推定・タイトル・サークル・作者・ネタ・本の種別・版・入手元・ファイル)。巻の順に並べ、列で並べ替えられる。
- 絞り込み: すべて / 1 巻を推定したシリーズ / 総集編 / 版・入手経路の印がある本を含むシリーズ / シリーズに入らなかった本。
- 検索: シリーズ名・サークル名・タイトル(全角・半角、大文字・小文字を問わない)。
- 上部に集計(冊数・シリーズ数・シリーズに入った本・巻の分かった本・推定した巻)。
- 読み込み: フォルダを選んで走査する、または CLI が書いた提案ファイルを開く。
- 行の組み立て(絞り込み・検索・並べ替え)は本体側に置いてテストし、画面は薄く保つ。確認は架空の名前のデータで行う。
- CSV(CLI の `series-list`)は、プレビュー一覧ができたら役目を終える。

プレビュー一覧のあとで、見直しの操作と書き出しを足していく。

- **見直し**: シリーズの組の採用・名前の修正・分割・統合。直した結果は確定した内容(`Confirmation`)として持ち、次の走査でも保つ。
- **書き出し**: Stackroom XML(StackNest と ShelfRow が取り込める)、qooViewer の保存データ JSON、ComicInfo。
  ShelfRow にはシリーズ・巻の欄が無いので、どの欄へ入れるか(タイトル・関連・キーワード)を選べるようにする。
  こうした第三者のアプリの欄への対応表は、ライブラリではなくこのアプリに置く。
- **説明の表示**: 選んだ本が、なぜその組になったか・ならなかったか(`Explanation`)。
- **好みの設定**: 方針(`policies`。総集編を本編に含めるか、版違いをどう数えるか、雑誌を年ごとにするか …)を、規則の編集より手前の
  ふつうの設定として出す。切り替えるとプレビュー一覧がその場で変わる。
- **規則の編集**: 既定値は同梱のまま、利用者の変更を別の JSON(差分)としてアプリの保存領域に保存し、以降はそれを使う。
  **初期化ボタン**で変更を消し、既定値に戻す(退避してから消す)。`rules-bundle` の書き出し・読み込みで、ほかのアプリ(CLI・qooViewer)と持ち運べる。
- **フィードバック**: 直した結果から、全語を架空の名前に置き換えた例を作り、利用者が中身を確かめてから送れるようにする(送り先は別に決める)。
- 通信はしない(フィードバックを送る操作を除く)。端末内モデルは入れるとしても任意の機能にする。
- 配布の形(署名・公証・サンドボックス、App Store か)は、この段階で決める。

**終わりの条件(プレビュー一覧)**: 両方の蔵書で CSV と同じ内容を GUI で見られる。絞り込み・検索・並べ替えのテストが通る。

## 段階 3: qooViewer への組み込み(時期未定)

- Swift Package として追加し、ブランチとリビジョンの両方で固定する(フォークと同じ扱い)。
- 「メタデータの編集」の初期値を qooMeta の提案にする。登録済みの本は確定した内容(`Confirmation`)として渡す。確定は今までどおり
  利用者の「登録」。本の増減は `ProposalIndex` の差分で追う。ファイル名だけで判定できるので、フォルダの権限は増えない。
  qooViewer の DB では「シリーズが空」は未入力の意味なので、`.notInSeries` ではなく `.fields` として渡す。`SeriesID` は保存しない。
- qooViewer のファイル名の規則を qooMeta の規則 JSON に置き換える(利用者が育てた規則を移す手段を用意する)。
  本の種別の語彙は qooViewer の設定に置く。
- ネタ・版なども保存するなら SwiftData のモデル変更になる(`StoreSchemaGuard` の世代と、開き直しのテストが要る)。

## 規則の中身の課題(形式の作業とは別に進める)

例のファイルに形を足してから直す。

- **書き手の同定**: サークル名の表記揺れ・改名で組が割れる。サークル名・作者名・フォルダの
  どれかが共通なら同じ書き手とみなす案(作者名は同じフォルダにある場合に限る。合同誌でつながりすぎないように)。
- **商業の単行本・雑誌向けのプロファイル**: 今は同人誌向けのフォーマットだけで、当てはまらない名前は簡易な解析に回っている。
- **続編の総集編**(「X2総集編」): 総集編の直前の数字を収録範囲として読むので、「X 総集編」の 2 巻になる。
- **同じタイトルの本が 2 つあるだけの組**: シリーズにはしないが、重複の候補として示すかどうか。
- 版の印の「新版」「旧版」が、語の一部(「最新版」)にも当たる。

## 保守

- **QooFormat の同期**: qooLibrary から写したコードの出どころ(コミット)を README に書いてある。qooLibrary 側の修正を取り込む手順
  (同じファイルを写し直し、変えたところ — 文言の準拠の削除とコメントの置き換え — を当て直す)をスクリプトにし、差分を確かめられるようにする。

## 決めずに残していること

- フィードバックの送り先。
- GUI アプリの配布の形。
- 利用者の変更のファイルの名前と、各アプリでの置き場所の細部。
