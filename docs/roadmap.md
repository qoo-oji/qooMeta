# 実装計画

2026-09-19 時点の計画。qooMeta は最終的に次の 2 つの形で使えるようにする。

1. **ライブラリ**: 依存パッケージとして qooViewer に組み込み、qooViewer がファイル名からメタデータを作るのに使う。
   qooViewer の今のファイル名の規則(ファイル名フォーマット・除外文字列・巻数フォーマット)は、最終的に qooMeta に置き換える。
   StackNest や ShelfRow のような蔵書管理アプリに組み込んでも十分に使える、汎用の API にする。**qooViewer への組み込みの時期は未定**。
2. **単独の GUI アプリ**: qooViewer とは独立させ、StackNest や ShelfRow の利用者も使えるようにする。このリポジトリの `App/` に置く。

関連する設計: [rules-format-design.md](rules-format-design.md)(規則ファイルの形式の第 2 版)、[api.md](api.md)(API 仕様)。

## 構成

```
qooMeta
├─ QooMetaKit      本体。名前の解析・シリーズ・巻・版・推定、規則の組み立てと検証、ProposalIndex、
│                  フィードバックの例づくり。Foundation だけに依存し、macOS 15 以降。QooFormat は内部に置く
├─ QooMetaRules    規則ファイルの読み込み(同梱の既定値 + 利用者の変更)、書き出し、初期化
├─ QooMetaExport   Stackroom XML・qooViewer JSON・ComicInfo・利用側の欄への対応(FieldMapping)。Data を返す
├─ QooMetaScan     フォルダの走査(名前と属性だけ)
├─ QooMetaAI       端末内モデル(任意、macOS 26 以降)
├─ qoometa         CLI(検証・一括処理・規則の確認)
└─ App/            GUI アプリ(SwiftUI)
```

## 進め方の約束(全段階に共通)

- **結果を変えない移し替え**では、両方の蔵書と公開データで「本と組の中身」が 1 冊も変わらないことを確かめてから進む
  (前後の出力のハッシュを比べる。名前は出さない)。規則そのものを変えるときは、変わった件数と形を集計で確かめる。
- 例・テストの名前は架空のものだけ。コミットの前に禁止語の検査を通す。
- 説明の文書(rules.md・api.md)は、実装と同じ変更の中で直す。

## 段階 0: 規則ファイルの土台(形式の第 2 版)

規則は最初のサンプルにすぎず、利用者のフィードバックで中身を育て、形式も広げていく。その土台を先に作る。

1. 読み込みの流れを作る: JSON を型なしで読む → 版を移す(第 1 版 → 第 2 版) → 重ね合わせる → 検証する → 組み立てる。
2. 規則の登録簿を作る(規則の `type` ごとの引数・既定値・必要な版 `since`)。書き間違いはエラー(位置と近い綴りの候補)、
   新しい版の規則は飛ばして警告。
3. 今のコードの判断を、ID の付いた規則として 1 つずつ移す(組の作り方・例外・名前の整え方・版と入手経路・総集編・巻の読み方)。
   コードに埋め込んである読み方(ローマ数字・雑誌の号 …)も規則にする。語の一覧は名前付きの `lists` に集める。
4. ファイル名のフォーマットをプロファイルに分ける(今は同人誌向けの 1 つ)。
5. 同梱の既定値を第 2 版で書き直す。
6. 利用者の変更(差分の JSON)を重ねる仕組み: `$add` / `$remove` / `$replace`、ID 単位の変更と無効化。初期化は差分を消すこと。
7. 例のファイル(`qoometa.examples`。架空の名前だけ)を作り、同梱する。今の単体テストのうち移せるものを移す。
8. 規則の上限(大きさ・語数・正規表現の安全性)の検査。
9. JSON Schema を登録簿から作り、`schema/` に置く。
10. CLI: `qoometa rules validate`(検査)、`rules show`(重ねた結果と出どころ)、`rules test`(例で確かめる)。
11. docs/rules.md を第 2 版の説明に書き直す。

**終わりの条件**: 第 2 版の既定値で、両方の蔵書と公開データの結果が今と同じ。第 1 版のファイルも読める。
例のファイルが全部通る。書き間違いの JSON でエラーの位置と候補が出る。

## 段階 1: ライブラリとして使える形にする(api.md)

1. モジュールを分ける(QooMetaKit / QooMetaRules / QooMetaExport / QooMetaScan / QooMetaAI)。本体は macOS 15 以降、
   端末内モデルだけ macOS 26 以降。
2. 本体を純粋な計算にする: グローバルな状態(今の `RuleFiles` の固定の読み込み)をなくし、`CompiledRules` を受け取る。
   ファイルの読み書き・ログ・通信をしない。
3. 入力を `BookInput`(利用側の不透明な ID・名前・フォルダ・確定済みの値 `ConfirmedMetadata`)に、語彙を `Vocabulary` にする。
   確定済みの値に従う処理(確定したシリーズ名・巻・「シリーズではない」)を足す。
4. `parseName`(1 冊)、`propose`(一覧。同期版と、取り消し・進み具合付きの非同期版)、`ProposalIndex`(変わった分だけ計算し直す)。
5. 出力を `ProposalSet` / `BookProposal` / `SeriesProposal` / `Volume` にし、決まった順で返す。表示の言葉は返さない。
   トレース(効いた規則の ID)は任意。
6. `QooMetaExport`: `FieldMapping`(Stackroom・qooViewer・ComicInfo・ShelfRow)と `fields(_:mapping:)`、Stackroom XML・qooViewer JSON。
   XML はエスケープ。書き出しは Data を返すだけ。CSV は API に含めない。
7. `QooMetaRules`: `RuleOverrides`(利用者の変更の編集・保存用の Data)、`checkExamples`。
8. `makeFeedbackExample`(直した結果を、形を保って架空の名前に置き換えた例にする)を本体に置く。
9. 入力の上限(`InputLimits`)、正規表現の時間の上限。
10. CLI を新しい API の上に作り直す。`qoometa bench` で性能を測る(1 万冊の一括、1 冊の追加)。
11. `public` の整理。試しの API は `@_spi(Experimental)`。

**終わりの条件**: CLI の結果が段階 0 と同じ。本体がファイル・ログ・通信を使わない(テストで確かめる)。`ProposalIndex` の
差分の計算が一括の計算と同じ結果になる(テストで確かめる)。性能の目安を測って docs に書く。

## 段階 2: GUI アプリ

最初に**プレビュー一覧**を作る(利用者の要望。CSV は見づらいので、見直しは GUI で行う)。

- **プレビュー一覧**: 左にシリーズの一覧(シリーズ名・サークル・冊数・巻の範囲・推定の有無)、右に選んだシリーズの本の一覧
  (巻・推定・タイトル・サークル・作者・ネタ・本の種別・版・入手元・ファイル)。巻の順に並べ、列で並べ替えられる。
- 絞り込み: すべて / 1 巻を推定したシリーズ / 総集編 / 版・入手経路の印がある本を含むシリーズ / シリーズに入らなかった本。
- 検索: シリーズ名・サークル名・タイトル(全角・半角、大文字・小文字を問わない)。
- 上部に集計(冊数・シリーズ数・シリーズに入った本・巻の分かった本・推定した巻)。
- 読み込み: フォルダを選んで走査する、または CLI が書いた提案ファイルを開く。
- 行の組み立て(絞り込み・検索・並べ替え)は本体側に置いてテストし、画面は薄く保つ。確認は架空の名前のデータで行う。
- CSV(CLI の `series-list`)は、プレビュー一覧ができたら役目を終える。

プレビュー一覧のあとで、見直しの操作と書き出しを足していく。

- **見直し**: シリーズの組の採用・名前の修正・分割・統合。直した結果は `ConfirmedMetadata` として持ち、次の走査でも保つ。
- **書き出し**: Stackroom XML(StackNest と ShelfRow が取り込める)、qooViewer の保存データ JSON、ComicInfo。
  ShelfRow にはシリーズ・巻の欄が無いので、どの欄へ入れるか(タイトル・関連・キーワード)を選べるようにする。
- **規則の編集**: 既定値は同梱のまま、利用者の変更を別の JSON としてアプリの保存領域に保存し、以降はそれを使う。
  **初期化ボタン**で変更を消し、既定値に戻す(退避してから消す)。規則の書き出し・読み込みで、ほかのアプリ(CLI・qooViewer)と持ち運べる。
- **フィードバック**: 直した結果から、架空の名前に置き換えた例を作り、利用者が中身を確かめてから送れるようにする(送り先は別に決める)。
- 通信はしない(フィードバックを送る操作を除く)。端末内モデルは入れるとしても任意の機能にする。
- 配布の形(署名・公証・サンドボックス、App Store か)は、この段階で決める。

**終わりの条件(プレビュー一覧)**: 両方の蔵書で CSV と同じ内容を GUI で見られる。絞り込み・検索・並べ替えのテストが通る。

## 段階 3: qooViewer への組み込み(時期未定)

- Swift Package として追加し、ブランチとリビジョンの両方で固定する(フォークと同じ扱い)。
- 「メタデータの編集」の初期値を qooMeta の提案にする。登録済みの本は `ConfirmedMetadata` として渡す。確定は今までどおり
  利用者の「登録」。本の増減は `ProposalIndex` の差分で追う。ファイル名だけで判定できるので、フォルダの権限は増えない。
- qooViewer のファイル名の規則を qooMeta の規則 JSON に置き換える(利用者が育てた規則を移す手段を用意する)。
  本の種別の語彙は qooViewer の設定に置く。
- ネタ・版なども保存するなら SwiftData のモデル変更になる(`StoreSchemaGuard` の世代と、開き直しのテストが要る)。

## 決めずに残していること

- 安定版(1.0)にする時期と範囲(状況を見て決める)。
- フィードバックの送り先。
- GUI アプリの配布の形。
- 利用者の変更のファイルの名前と、各アプリでの置き場所の細部。
